## ❄️ Welcome to Winter of Code 6.0

**Winter of Code 6.0 (WOC 6.0)** is a three-month open-source contribution program organised by **Google Developer Groups on Campus IIIT Kalyani**. It brings together students, aspiring developers, designers, and technology enthusiasts to learn through collaboration and contribute to real-world open-source projects.

Whether you are opening GitHub for the first time or already have experience building software, WOC gives you an opportunity to explore active codebases, work with open-source organisations, learn from experienced mentors, and make contributions that matter.

Inspired by the contribution-driven model of **Google Summer of Code (GSoC)**, the program encourages you to move beyond tutorials and learn how software is built, maintained, reviewed, and improved by communities.

> **You don't need to be an expert to get started. You need curiosity, consistency, and the willingness to learn.**

During WOC, you will work with participating open-source organisations and their projects. Depending on the project you choose, you may:

## 🌱 New to open source? Start here.

Open source is software whose source code is made available for people to inspect, use, improve, and contribute to, according to its licence. Projects are often maintained by communities of developers who collaborate using platforms such as GitHub.

You do not have to create an entire application from scratch to contribute. A contribution can be a bug fix, a test, a documentation improvement, a design enhancement, or a new feature.

### A few terms you'll encounter

| Term | What it means |
| --- | --- |
| **Repository (repo)** | The project space containing its source code, files, documentation, and version history. |
| **Issue** | A reported bug, requested feature, question, or task that needs attention. |
| **Fork** | Your own copy of another GitHub repository, where you can make changes independently. |
| **Clone** | Downloading a repository to your local computer so you can work on it. |
| **Branch** | A separate line of development where you can make changes without directly modifying the main branch. |
| **Commit** | A saved snapshot of your changes, accompanied by a message describing them. |
| **Push** | Uploading your local commits to a remote repository, such as your GitHub fork. |
| **Pull Request (PR)** | A request asking project maintainers to review and merge your changes into the original project. |
| **Code review** | The process of checking proposed changes and sharing feedback before they are merged. |
| **Maintainer** | A person responsible for guiding, reviewing, and maintaining a project. |

### 🧰 Tools worth getting familiar with

- **Git:** Tracks changes in your code and helps you work with branches and commits.
- **GitHub:** Hosts repositories and supports issues, pull requests, discussions, and collaboration.
- **Command line / Terminal:** Lets you run Git commands, install dependencies, and execute project tools.
- **Project-specific tools:** Depending on the repository, you may use programming languages, frameworks, package managers, testing tools, or design software.

If you're new, begin by learning the basics of Git and GitHub, setting up your development environment, and reading the README and contribution guidelines of the project you want to work on.

## 🛠️ How contributing works

The exact process can differ between organisations. A typical GitHub contribution workflow looks like this:

1. **Find a project:** Browse the participating organisations and project listings on the [WOC website](https://www.winter-of-code-6.tech/). Check the project's purpose, tech stack, requirements, and expected work.
2. **Understand the repository:** Read its README, contribution guidelines, licence, issue descriptions, and setup instructions. Explore the code before proposing a change.
3. **Choose an issue:** Look for an issue that matches your current skills and interests. If something is unclear, ask questions in the project's accepted communication channel before starting.
4. **Set up locally:** Fork the repository if required, clone your fork, install dependencies, configure the project, and run it locally. Follow the repository's setup instructions.
5. **Create a branch:** Make your changes on a separate branch. Keep the work focused and avoid mixing unrelated changes.
6. **Test your changes:** Run the relevant tests, checks, or build commands. Verify that your change works and does not unintentionally break existing functionality.
7. **Commit and push:** Save your work in clear, meaningful commits and push your branch to your GitHub fork.
8. **Open a pull request:** Describe what you changed, why you changed it, and how you tested it. Link the related issue when appropriate.
9. **Respond to review:** Read maintainer feedback, make requested improvements, push follow-up commits, and keep the discussion constructive.
10. **Get it merged:** Once the maintainers approve and merge your pull request, your contribution becomes part of the project.

**Remember:** A pull request is not complete just because it is submitted. Be ready to communicate, test, revise, and learn throughout the review process.

## 🧭 Your WOC 6.0 journey

WOC 6.0 takes you from discovering projects to presenting the work you have completed.

### 1. Explore and connect
Register through Devfolio, explore participating organisations and projects on the official website, and join the official community channels announced by the organisers. Read project requirements and get familiar with the communities you are interested in.

You can choose **up to three projects across three distinct organisations**. Prepare a tailored proposal for each selected project, explaining your understanding of the problem, proposed approach, milestones, and execution plan. Follow the instructions and deadlines announced for submissions.

Complete your planned work, prepare your final submission, and showcase your contributions. The program concludes with a closing ceremony recognising projects, collaboration, and contributor achievements.

## 💡 Tips to make your contribution count

- **Start with the documentation.** Read the README, contribution guide, project setup, and code of conduct before changing anything.
- **Understand before you edit.** Run the project and trace how the relevant part of the code works.
- **Start small.** A focused, well-tested fix is more valuable than a large change you cannot explain.
- **Communicate early.** Ask clear questions and share your approach when you are unsure.
- **Write useful commits.** Use concise messages that explain the change.
- **Make your pull request easy to review.** Explain the problem, your solution, relevant screenshots where applicable, and the tests you ran.
- **Treat feedback as learning.** Reviews are a normal part of collaborative software development.
- **Be consistent.** Make steady progress and keep your mentors or maintainers informed.
